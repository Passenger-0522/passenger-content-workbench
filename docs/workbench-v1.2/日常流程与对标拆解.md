# 日常流程与对标拆解

配合 PRD v1.2，更新于 2026-10-10。

## 1. 最终分工

- Gemini 默认写全部平台文案，包括 X；基本输入和产物可以只是正文。
- Codex 读正文，自行决定封面上的表达、构图和图片，不要求 Gemini 预写封面标题。
- 网站保存项目、选题、原文、账号数据、任务、素材和发布进度。
- Obsidian 可选保存长期阅读资料与拆解笔记，不承担发布状态与每日计数。
- 第一版手动发布；后续再研究投递各平台草稿箱。

平台最终发布必须的标题可以在版本编辑中补齐。没有标题也能先捕获想法、写正文或制作封面。

## 2. 你每天的入口

在 Antigravity 说：“这是我今天想写的……”“收藏这篇文章……”“把这个博主放进对标库……”即可进入对应流程。

实现方式：Antigravity 按项目规则保存原始输入与结构化捕获包，网站后台监听并入库，生成真实回执。它不需要购买模型 API，也不需要读取 Codex 的聊天历史。后台离线时显示待导入，恢复后继续；相同捕获包不重复建立数据。

这是待实施的功能约定；本次更新了设计文档，没有接通当前网站。

## 3. 首页需要让你一眼看懂的事情

| 视图 | 回答的问题 |
| --- | --- |
| 今日待发 | 已准备好、计划今天发布的各平台版本有哪些？ |
| 逾期未发 | 哪些内容错过原定日期？ |
| 未排期 | 哪些完整内容还没决定什么时候发？ |
| 制作中 | 哪些正文、图、封面、视频或排版还缺？ |
| 选题待做 / 已做 | 哪些想法还没做，哪些已经有完成的内容？ |
| 今日目标 | 各平台实际发了多少，还差多少？ |

“选题已做”“发布包准备好”“平台已发布”分别保存。一个项目 X 已发、公众号未发，公众号仍然显示待发；收藏与拆解不算自己已经做过内容。

## 4. 对标库不只是存一个博主名字

一层保存人物 / 品牌，另一层保存每个平台账号；跨平台关联需要确认。同名账号不自动合并。

账号保存主页、稳定 ID、昵称、内容方向、为什么值得对标、代表文章、关注级别。粉丝数据保存带日期和来源的快照，而不是只覆盖一个数字。

能够真实自动采集的平台再接接口；其他平台支持手动录入或有依据的导入。未知不是 0，“1.2 万”保留为约数，最后有效值可以显示，但必须带时间。历史增长从已有快照计算，不能为新加的账号伪造过去曲线。

粉丝量用于理解账号阶段，还要看内容方向、受众、近期更新与具体作品，不只按“大号”排序对标对象。

## 5. 给一个文章链接之后

先把它保存为来源资料：原链接、作者、原时间、可读原文、抓取时间和完整性。内容文件放本地，数据库保存索引和关系。可读时保存正文 Markdown 和原件；拿不到全文则准确显示仅链接或部分正文。

之后是三个独立动作：

1. **标记为对标文章**：你认为值得研究，补一句为什么收藏。
2. **拆解文章**：Gemini 分析受众、选题、开头、结构、证据、节奏、视觉和结尾，并说明哪些判断缺数据。
3. **转成自己的选题**：选择一种值得借鉴的方法，补充你的观点、实测或案例，进入待做列表。

文章拆解的核心交付是“你下一条具体能做什么、需要补什么材料”，而不仅是一份文章概括。收藏、拆解、创作和发布四种状态不能混为一谈。

## 6. 给一个博主之后

选择样本范围，分析近期栏目、题材、形式、更新频率、封面 / 开头模式、系列结构与可观察的内容变化。样本包括常规作品和高表现作品，不只挑几个所谓爆款。

报告标明收集了哪些内容、哪个时间段、哪里有缺口。“样本最早发文时间”不等于“真正起号时间”，注册日期也不等于开始持续创作的日期。

结论可以转成选题、栏目或一次试验计划。不会因为对标博主一天发很多，就自动提高你的全部平台目标。

## 7. 下载进数据库，还是放进 Obsidian？

推荐两者配合：

| 保存位置 | 保存什么 |
| --- | --- |
| 网站数据库 | 索引、选题、任务、账号快照、关联关系、制作与发布状态 |
| 网站本地文件 | 原文、Markdown、图片、视频、拆解正文 |
| Obsidian，可选 | 需要长期阅读的来源资料卡、拆解报告、自己的知识笔记 |

网站里也能阅读原文，不要求为每次查看切换到 Obsidian。第一版先支持 Markdown 下载；真正启用 Vault 投递时，遵守现有 Vault 规则，保留原件与来源，避免重新建库。

初期单向导出，Obsidian 不自动反向改写网站工作状态。原文章、AI 分析与你自己的判断分开记录，可以用 ID 和链接联系起来。

## 8. 拆解之后怎么发

先确定自己的新内容价值，再选适合的平台和形式。一个母稿可以形成公众号完整文章、X 的独立观点帖、小红书步骤图或短视频，但不要求每次全平台发布。

制作顺序取决于素材是否齐全；发布顺序取决于你可用的时段、平台已有数据和待发量。没有历史数据时做可记录的小范围试验，不承诺某个固定时刻必然有流量。

发布后回填数据，再按 24 小时 / 7 天复盘决定是否做续篇、补充解释或转成另一种形式。不把发出一篇文章当作这个选题的唯一终点。

## 9. 后续草稿箱投递

保留为 P2：已审阅内容 → 指定平台 / 账号草稿箱 → 回读核验 → 用户在平台发布。

每个平台核验自己的能力与权限，不承诺一个通用接口覆盖全部平台。草稿成功不算已经发布；正文 / 封面 / 媒体上传部分失败要明确显示；本地修改后提醒远端草稿是否还是旧版。

第一版不因这个后续想法阻塞现有复制 / 下载闭环，也不执行远端投递。

## 10. 现在值得补的三件事

1. **收藏理由和独立状态**：避免囤了很多文章，却不清楚为何收藏、是否拆解、是否实践。
2. **快照与样本证据**：粉丝、时间、文章表现留来源，避免把不完整数据当成结论。
3. **拆解直接转选题并复盘**：研究成果进入待做和发布计划，完成后回来记录是否有效。

当前功能范围已经能形成完整工作流；先跑通这三件事和自动入库，不再增加新的大模块。
